## 實際完成

### 伺服器權威領域引擎

`app/Domain/Game/` 是唯一的規則計算來源。結算順序固定為 [遊戲設計](../GAME-DESIGN.md) §3.3：

```text
驗證 → 扣惡意 → 套情境修正 → 算核心衝擊 → 扣防線 → 更新印記／連攜／打斷
→ 核心歸零即勝 → 城市回應 → 更新效果與冷卻 → 檢查回合耗盡 → 產生下回合預告與回復
```

驗證階段**只讀狀態**，任何一項不過就丟 `InvalidActionException`，所以不合法的提交不會消耗回合或惡意。

已實作：技能成本／冷卻（`ready_on_turn`）、城市防禦預告、破綻、適應抗性、階段轉換（重整倒數）、凍結快照、事件序列、重送去重、回合版本與存檔。

**`rules_version 1.0.0` 完全沒有亂數。** 城市行為由關卡預告表決定，因此重播不需要保存亂數狀態，且「相同輸入得到相同事件與結局」是結構性成立而非統計性成立。

### 事件契約

每則事件含 `sequence`、`turn`、`type`、`actor`、`target`、`reason_code`、`before`、`delta`、`after`、`cue_id`，足以解釋傷害、護盾、印記、抗性、修復與勝負。`cue_id` 讓 P04／P06 挑演出，客戶端不再算一次傷害或決定勝負。

真實 HTTP 一次施招的事件序列：

```text
action_accepted → impact → defense_shift → sigil_gain → city_reinforce → turn_advanced
```

### HTTP 契約

六個介面全部掛在 `web` middleware group 底下（`bootstrap/app.php` 的 `then` 回呼），網址雖然是 `/api/v1` 仍走工作階段與 CSRF：

| 介面 | 用途 |
|---|---|
| `GET /api/v1/levels` | 關卡、解鎖狀態、最佳成績、來源品質 |
| `POST /api/v1/runs` | 建立局、綁定快照與規則版本 |
| `GET /api/v1/runs/{run}` | 續玩、目前版本、可用行動清單 |
| `POST /api/v1/runs/{run}/actions` | 提交行動 |
| `GET /api/v1/runs/{run}/replay` | 已結束對局的重播資料 |
| `GET /api/v1/data-status` | 去秘密化的來源品質 |

錯誤語意：`expected_version` 過期或 `action_id` 帶不同 payload → 409；規則不合法 → 422 且交易不寫入；不是自己的局 → 404（不用 403 洩漏 run 存在）。成功一律 200，首次提交與重送回同一個狀態碼。

### 資料真的改變決策

`ScenarioModifierCalculator` 把 P02 的正規化快照換算成每系 −15%～+15%。實際連線後的開局回應（本機 2026-09-08）：

```text
scenario water=0.0065 reason=reservoir_and_demand
```

這個 0.0065 來自當日水庫 `storage_index` 與新竹園區 `demand_index` 的實際值，不是寫死的常數。缺欄位一律回中性 0 並標 `missing_inputs`；只有 `in_hsinchu = true` 的園區進入需求訊號。

### 存檔

`campaigns`／`runs`／`run_actions` 三張表。擁有者以不可猜測的 `anonymous_id` 綁 HttpOnly session；`run_actions` 對 `(run_id, action_id)` 有唯一索引，重送直接回放該列不重新結算。

### 平衡與模擬

`docs/BALANCE.md` 鎖版所有公式與常數。`php artisan game:simulate` 跑（關卡 × 情境 × 策略 × seed）矩陣，五個策略：`random`、`single-water`、`legacy-cycle`（舊版三系集印記再放終招）、`greedy`（讀預告）、`planner`（會布局）。

前瞻策略用**真正的引擎**試算每個合法行動，不複製傷害公式；只往前看一步，那正是玩家在畫面上看得到的資訊，不偷看未來回合。

## 自我驗收與修正

交付後對照 [技術規格](../TECHNICAL-SPEC.md) 逐項重讀，找到三項**規格明文要求但實作漏掉**的缺項，全部補上並補測試。

### 1. 沒有條件版本更新，存在 lost update 窗口（嚴重）

技術規格 §5 寫得很清楚：「採條件版本更新避免雙分頁覆寫；**不依賴 SQLite 不支援的 row lock 語意**」。原本的 `submit()` 用了 `lockForUpdate()`——而 Laravel 的 `SQLiteGrammar::compileLock()` 直接回傳空字串，那行程式碼只是給人安全感。

用一個會在 `apply()` 期間搶先寫入的引擎把窗口固定重現，證實原本的結算會直接覆蓋掉對方的版本：

```text
修正前  搶先寫入之後仍然結算成功，代表發生了 lost update
修正後  RunConflictException(stale_version)，交易回滾，沒有行動紀錄、局面未動
```

修正：拿掉 `lockForUpdate()`，改用 `where('version', $observedVersion)->update(...)` 並檢查影響列數；不是 1 就丟 409 讓整個交易回滾。

回歸測試：`ConcurrentSubmitTest::test_a_competing_write_during_settlement_is_rejected_instead_of_overwritten`。

### 2. 行動端點沒有限流

技術規格 §6 的錯誤語意列了「限流：429，給可重試時間」，但路由上沒有任何 throttle。補上 `throttle:game-actions`（每分鐘 60 次），超過回 429 並帶 `Retry-After`。

限流 key 用工作階段裡的匿名識別，不是 session id——session id 在某些情境下每次請求都會重新產生，那樣等於沒有限流（實測 `X-RateLimit-Remaining` 永遠停在 59）。也不用 IP，避免同一個 NAT 後面的玩家互相拖累。

回歸測試：`RunApiTest::test_the_action_endpoint_is_rate_limited_and_says_when_to_retry`。

### 3. SQLite `busy_timeout` 未設定

技術規格 §5 要求「開啟外鍵、驗證 busy timeout 與重試」。外鍵預設已開，但 `busy_timeout` 是 `null`，代表一碰到寫鎖就立刻丟 `database is locked`（500）而不是等待。設為 5000 毫秒，可用 `DB_BUSY_TIMEOUT` 覆寫。

回歸測試：`RunApiTest::test_foreign_keys_and_a_busy_timeout_are_enabled_on_sqlite`。

## 規格偏差與決策

1. **平衡數值大幅調整。** [遊戲設計](../GAME-DESIGN.md) §3 的初稿在任何策略下都無法通關（全表 0% 勝率）。調整項目、前後值與理由列在 [BALANCE.md §6](../BALANCE.md)。這是規格預期的 P03 工作，不是擅自改設計。
2. **破陣成本 4→5、冷卻 2→3。** 初稿的「三系破陣輪替」無縫銜接又每回合吃到連攜，是壓倒性最優解，貪心與規劃策略打出**完全相同**的行動序列。調整後兩者才真正分歧。
3. **城市同時只維持一道護盾。** 初稿沒有規定護盾上限，實測發現會滾雪球到玩家完全打不進核心。新護盾取代舊護盾，並寫進 BALANCE.md。
4. **重整倒數改為到期才生效。** 原本實作在倒數第一回合就完成修復，等於玩家只有一次干擾機會，與「兩回合倒數、需要兩次不同系干擾」的設計矛盾。
5. **`rules_version 1.0.0` 不使用亂數。** [遊戲設計](../GAME-DESIGN.md) §6 允許「首版能完全無隨機」；選擇無隨機讓重播不必保存亂數狀態，也讓 P07 的反事實比較不會因多抽一次亂數而失真。seed 仍保存在 `runs`，目前只驅動模擬策略。
6. **行動 API 一律回 200。** Laravel 預設對「剛建立的模型 + POST」回 201，會讓首次提交與重送回不同狀態碼，客戶端要分兩條路處理同一個結果。
7. **只實作三關。** 依開發計畫「先用三個代表情境驗證規則，不急著複製 13 份 UI」；13 關在 P05。

## 尚未完成或未驗證

- **沒有真人試玩。** 機器策略勝率不是真人體驗證據。`greedy` 與 `planner` 都 100% 不代表關卡簡單——前瞻策略用真引擎試算每個合法行動，人類做不到。難度標籤、卡點紀錄與難度曲線屬 P08。
- **沒有 UI。** 本階段只有 JSON 介面與 Vue 頁面殼；選關、戰前情報、施招演出、過場與音效屬 P04／P06。
- **只有三關、三組單純情境。** 低／中／高是三系同時取上下界；實際快照會出現混合情形（例如水系偏高、土地偏低），P05 需要補混合情境的可解性驗證。
- **`data_snapshots` 清理仍未啟用。** `runs.snapshot_ids` 現在會引用快照，但 `SnapshotRepository::prune()` 尚未加入「排除仍被對局引用的 snapshot_id」的保護，因此維持不排程。這是 P05 之前必須補的。
- **效能未量測。** TECHNICAL-SPEC §8 的 p95 < 800 ms、20 個同時活躍對局等目標尚未壓測。
- **存檔到期與容量清理未實作。** 30 日未活動到期、每玩家最近 20 局詳細重播的保留政策尚未排程。
- **重播端點只回原始資料。** 關鍵回合、因果鏈與反事實比較是 P07 的工作，本階段只保證資料齊全。

| 項目 | 結果 | 補充 |

| 數據平台首頁 | **逾時** | DNS 成功解析為 `163.29.185.46`，TCP 連線在 20 秒內未建立（`tcpMs=null`） |

五項全部在 DNS 解析成功後卡在 TCP 連線階段（20 秒逾時，無 RST、無錯誤訊息），型態一致，指向目的地網路（`163.29.185.0/24`，新竹縣政府自有網段）主動丟棄或未回應來自本主機出口 IP 的連線，而非 Hostinger 端阻擋出站流量。

## 對照測試（排除本機其他因素）

同一台主機上另外測試：

- `https://www.google.com/`：`200`／`302`，連線正常。
- `https://github.com/`：`200`，連線正常。
- `https://data.gov.tw/`（Cloudflare 代管）：`200`，連線正常。
- `ping` 到 `163.29.185.46`：100% 封包遺失（ICMP 也無回應，與 TCP 逾時型態一致）。

代表本主機一般對外連線（含 IPv4、TLS）正常，也能連到其他掛在 Cloudflare 之類全球 CDN 的台灣網域；問題集中在直接連往新竹縣政府自有機房 IP 的這三個主機（`dip.hsinchu.gov.tw`、`ws.hsinchu.gov.tw`、`www.hsinchu.gov.tw`，同屬 `163.29.185.x`）。

## 判讀

依 [api-probe/README.md](README.md) 的判讀限制，單次逾時不能單獨證明地區封鎖；但本次已排除「Hostinger 出站被擋」與「目標網域整體離線」兩種替代解釋（同主機能連國際站台與 Cloudflare 代管的台灣站台），且五個目標、三個不同 IP 一致逾時，型態很像新竹縣政府網段對非台灣來源 IP 做了邊界防火牆限制（常見於部分縣市政府網站僅允許國內連線）。

**建議**：在規劃正式串接前，先向新竹縣數據平台或資訊單位確認是否有對海外 IP 的存取限制、是否提供可從海外呼叫的正式 OpenAPI、或是否需要申請白名單／改走國內代理。若確認海外連不到，此 repo 現有的 Hostinger（歐洲／東南亞機房）部署方式無法直接串接這三個主機，須改成：由台灣境內的伺服器代理轉發，或改用縣府若有提供、掛在 Cloudflare／data.gov.tw 等 CDN 之上的公開資料介面（此類目前測試可正常連線）。

原始探測結果（含每個項目的 DNS／TCP／逾時明細）：見執行當下產出的 JSON，未納入版本控制。

## 追加對照：同主機、同架構打中央氣象署開放資料平台

為排除「是不是串接方式（Node.js `https` 模組）本身有問題」，另外在同一台主機上，用同帳號 `weather-map` 專案既有的 PHP 服務端程式（`api/CwaClient.php`，走 PHP `curl` 擴充套件、直接伺服器端呼叫，架構跟本次 Node 探測一樣是「伺服器對伺服器」，不是瀏覽器端呼叫）測試 `https://opendata.cwa.gov.tw/`：

| 測試 | 結果 |
|---|---|
| `curl`／PHP `curl` 連線首頁 | TCP 連線 68ms、HTTP 302，正常 |
| 帶正式 API 金鑰呼叫 `O-A0003-001`（觀測資料集）正式介面 | HTTP 401（金鑰失效／過期，但代表請求確實送達並被氣象署伺服器處理，不是逾時） |

結論：**中央氣象署開放資料平台完全沒有擋這台海外主機**，連線速度正常、也拿到了正常的業務層錯誤（401），而不是像新竹縣三個主機那樣連 TCP 都建立不起來。這排除了「Node.js 探測程式的連線方式有問題」這個假設——同一台主機、同樣是伺服器端直接呼叫，氣象署可以連、新竹縣自有機房不行。差異在目的地網路本身，不在串接方法。

換句話說：氣象局的開放資料平台本身沒有做地區限制（可能是因為它是全國性、對外開放給大眾與第三方應用使用的正式 API，架設方式也可能不同），而新竹縣政府自己機房那幾台（`163.29.185.x`）看起來確實對非台灣來源做了邊界限制。兩者不能類比，串接前仍需比照氣象局的模式，優先找新竹縣是否有掛在類似公開、對外開放的 API 服務，而不是假設所有 `.gov.tw` 都會擋。
